# Задание 2. Разделение системы на домены и моделирование потоков данных для поддержки ключевых бизнес-сценариев

## Разделение системы на домены

Архитектура TO BE

![Архитектура TOBE](./architecture-future_2_0_container_(to_be+domain).png)

Данный подход позволяет понятным образом расширять бизнес, по аналогии с описанными доменами (прим.Медицина) а также, произвести плавную миграцию от Legacy System к Data Mesh

**При этом важно понимать что Legacy System не является доменом! Это рудимент, который должен исчезнуть со временем.**

Ключевые принципы которыми мы также руководствовались при разделении:

1. Каждый домен управляет своими данными и сервисами
2. Строгое разделение данных между доменами
3. Независимое развитие каждого направления, домены не должны влиять друг на друга (за исключением платформенных сервисов)
4. Агрегированные данные для кросс-доменной отчетности через централизованную платформу
5. Масштабируемость (домены независимы, и мы можем расширять бизнес сколько угодно, алгоритмы понятны, все интеграции проходят через платформенные сервисы)
6. Каждый домен должен соответствовать бизнес направлению

По факту разделения на указанные домены мы получаем следующие приемущества:

1. Масштабируемость:

   1. Простой и понятный способ интеграции новых направлений в существующий бизнес
   2. Переход в облако и к распределенной среде также положительно влияет на масштабирование
   3. Снижение зависимости от монолитного DWH также повышает масштабируемость упрощая связи и логику за счет перетекания ее в отдельные домены
2. Безопасность:

   1. Данные изолированы, отсутствует сильная связь между доменами снижает риск компрометации данных других доменов
   2. Изоляция данных, повышает возможности для соблюдения требований 152ФЗ о персональных данных
3. Повышение Time To Market:

   1. За счет отсутствия сильных связей, каждый из доменов может развиваться независимо от остальныых
   2. Фокус только на своей бизнес области, ответственность только за свои данные
4. Улучшение качества данных:

   1. В каждом домене фокус только на своей бизнес области, ответственность только за свои данные
   2. Подход Data as a product также улучшает качество данных в частности за счет отдельных команд которые заботятся о качестве данных (+ они лучше знают данные с которыми работают)
